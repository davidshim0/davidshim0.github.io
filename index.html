I spent nearly nine years at Samsung, one of the largest DRAM vendors, and I now work on replacing DRAM, which would have done my bonus no favors at the time. The cost per bit of DRAM has stopped falling the way it used to. The device itself keeps improving, but the scaling has slowed in most of what matters: cost, latency, and energy efficiency. Alternative memories have been called emerging for at least a decade, and several are now good enough to put into a real system and cut the DRAM footprint substantially. What I enjoy is making that practical: redesigning the hardware on an FPGA, changing the kernel so placement decisions are fast and their overhead small, and redrawing the interface between the two.

I am advised by Philip Levis in the Stanford Information Networks Group, and much of this work is part of Stanford Differentiated Access Memory (DAM).

Research

Application read-only memory

Denser and cheaper memories bring constraints DRAM does not have: asymmetric read and write cost, limited endurance, and coarse write granularity. Commercial parts hid those behind a translation layer on the module, and the layer cost more than it saved. I work on the opposite arrangement, where the system exposes the constraints and the kernel manages them. Such memory is read-only to applications and written only by the kernel during migration, enforced with copy-on-write, which moves wear levelling off the device and lets the hardware get simpler rather than more complex.

Packet processing and memory bandwidth

Network interfaces now have enough compute to inspect traffic at line rate and nowhere near enough memory bandwidth to feed it. Packets arrive variable sized and out of order while the memory they land in is a contiguous address space divided into fixed-size pages, and translating between the two layouts costs copies that consume the bandwidth the analysis needed. With colleagues I work on addressing that lets software read a whole flow as one contiguous region, built and measured on FPGAs.

Placing data across unlike memories

Once a server holds several kinds of memory, the operating system has to decide what belongs where, and how often a page is touched turns out to be too coarse a signal. Two pages read equally often can perform very differently in the same memory, because memory-level parallelism, compression and read and write asymmetry all cut across access frequency. I am interested in what the hardware should tell the operating system about how well a page suits a given memory, and in measuring what deployed disaggregated memory actually costs.
