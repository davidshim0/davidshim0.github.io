Memory is the largest share of what a server costs, and the cost per bit of DRAM has stopped falling. My work is about what replaces it and what the system software around it has to do differently.

Application Read-Only Memory

Denser and cheaper memories bring constraints that DRAM does not have: asymmetric read and write cost, limited endurance, and coarse write granularity. Commercial parts hid those behind a translation layer on the module, and the layer cost more than it saved. I work on the opposite approach, where the system exposes the constraints and the kernel manages them. The central idea is that such memory is read-only to applications and written only by the kernel during migration, enforced with copy-on-write, which moves wear levelling off the device and lets the hardware get simpler rather than more complex.

Placing data across unlike memories

Once a server holds several kinds of memory, the operating system has to decide what belongs where, and how often a page is touched turns out to be too coarse a signal. Two pages accessed equally often can perform very differently in the same memory. I am interested in what the hardware should tell the operating system about how well a page suits a given memory, and in measuring what deployed disaggregated memory actually costs, including the capacity and latency tradeoffs of CXL expanders at datacenter scale.

Packet processing and memory bandwidth

Network interfaces now have enough compute to inspect traffic at line rate and nowhere near enough memory bandwidth to feed it. Packets arrive variable sized and out of order while the memory they land in is a contiguous address space divided into fixed-size pages, and translating between the two layouts costs copies that consume the bandwidth the analysis needed. With colleagues I work on addressing schemes that let software read a whole flow as one contiguous region, built on FPGAs to measure what they save.
